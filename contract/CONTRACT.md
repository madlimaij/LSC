# Rule Set contract 1.0.2

This is the contract between the Language Skill Compiler (`lsc`) and Legacy Navigator's CustomLanguageAdapter. It covers the Rule Set JSON file: what it contains, the rules it must follow, and how a consumer must apply it so that Navigator finds exactly what `lsc` tested.

The contract is published three ways, all generated from one source (`src/contract/`):

| Artifact | Use |
| --- | --- |
| `contract/rule-set.schema.json` | JSON Schema (draft 2020-12) of the file structure. Generated by `npm run contract:export`; do not edit by hand. |
| `contract/CONTRACT.md` (this file) | Rules JSON Schema cannot express (§5) and the matching semantics a consumer must implement (§6). |
| `src/contract/` | Zod schemas, TypeScript types, `RULE_TYPE_SPEC`, and the reference validator behind `lsc validate-ruleset`. |

Fixtures:
- `contract/fixtures/toylang.ruleset.json`: a valid Rule Set for the synthetic language `toylang`, one or more rules per rule type, both engines.
- `contract/fixtures/invalid/<rule>--<variant>.json`: each file breaks exactly one validation rule; `<rule>` is the rule code from §5.

Plan references: `docs/PLAN.md` §5 (contract), D1–D4, D6. Decisions made while implementing it: `docs/DECISIONS.md` D11–D14; approval at G1: D16; later changes: D19, D20, D21, D22 (history in §8).

## 1. Validating a Rule Set

A consumer must do both steps, in this order:

1. Read `contractVersion` and apply §2. Stop if it is not supported.
2. Validate the whole file. Either run `lsc validate-ruleset <file>` (exit code 0 = valid; `--json` for machine-readable output), or validate against `rule-set.schema.json` **and** reimplement every rule in §5.2.

JSON Schema alone is not enough: the files in `contract/fixtures/invalid/` whose names do not start with `schema--` or `contract-version--` pass the JSON Schema and are still invalid.

Error output of `lsc validate-ruleset` has one line per problem:

```
$.rules[2].captures: [captures-required-roles] type "call" requires capture role "callee"
```

that is: JSON path, rule code in brackets (§5), message.

## 2. Contract version and compatibility

`contractVersion` is the version of the file *format* and of the consumer behaviour this document prescribes (semver). This contract is **1.0.2**.

| Change to the format | Bump | Example |
| --- | --- | --- |
| A field is removed or renamed, its type or meaning changes, a rule type or engine is removed, or a file that was valid becomes invalid | major | renaming `captures` |
| Addition that keeps every older file valid and meaning the same | minor | new rule type (e.g. `branch_marker`, D1), new optional field, new engine |
| Wording, error messages or documentation only; no change to which files are valid or what they mean | patch | clarifying §6 text |

Consumer policy for a file with contract version `M.m.p`, when the consumer implements `1.0.x`:

- `M` ≠ 1: reject the file.
- `M` = 1 and `m` > 0: reject the file and ask for a consumer upgrade. The file may use rule types, fields or engines this consumer does not know, and all objects in the schema are closed (`additionalProperties: false`), so the 1.0 schema rejects it anyway.
- `1.0.p`, any `p`: accept.

A newer validator accepts older minors of the same major (a 1.2 validator accepts 1.0 and 1.1 files). Pre-release suffixes (`1.0.0-rc.1`) are not accepted in `contractVersion`.

Specifying consumer behaviour for a case this document previously left unspecified (an open question in §9), without changing which files are valid or any behaviour already specified, counts as a clarification: a patch bump. 1.0.1 is such a bump (§8 history, D20). So is replacing a provisional answer that §9 still listed as open with the project owner's decision, as long as validity does not change: 1.0.2 (D21, D22). Because a patch never changes acceptance, a consumer applies the behaviour of the patch level it implements (1.0.2 now) to every `1.0.x` file, and a producer must not rely on the `contractVersion` patch level to select consumer behaviour.

## 3. Content version (`version`) bump rules

`version` is the version of the rules inside the file (semver), assigned by `lsc export` (WP-10). The first export is `1.0.0`.

| Change between two Rule Sets for the same language | Bump |
| --- | --- |
| A rule removed or renamed (`id` changed), or its output meaning changed: `type` changed, capture roles added, removed or remapped | major |
| Rules added | minor |
| Patterns refined (regex, exact tokens, flags, `blockEnd`, `searchStrings`) with no change in meaning | patch |

When several apply, the largest wins. Navigator can treat a patch or minor update as safe to adopt automatically; a major update may change what its records contain.

## 4. Rule types and the Navigator mapping

Every rule has one `type`. The type fixes which Navigator record a match produces and which capture roles the rule must and may map. The same table is exported in code as `RULE_TYPE_SPEC` (`src/contract/rule-types.ts`).

| Rule type | Navigator record | Kind / mode | Required capture roles | Optional roles | `blockEnd` allowed |
| --- | --- | --- | --- | --- | --- |
| `module_declaration` | `symbols` | kind `module` | `name` | — | yes |
| `symbol_definition` | `symbols` | kind `function` or `procedure` (§4.1 item 3) | `name` | `kind` | yes |
| `call` | `relations` | kind `calls` | `callee` | `module` | no |
| `include` | `relations` | kind `includes` | `target` | — | no |
| `db_read` | `dbAccesses` | mode `read` | `table` | — | no |
| `db_write` | `dbAccesses` | mode `write` | `table` | — | no |
| `config_ref` | `configRefs` | — | `key` | — | no |
| `entry_point` | `entryPoints` | the `kind` capture's text, when present | `name` | `kind` | no |

`branch_marker` and `exit` are not rule types in 1.0 (D1). Adding them is a minor bump.

### 4.1 Mapping rules

This subsection is normative, like §6. Each applied match (§6.1) is mapped as follows:

1. **Low confidence.** Every match of a rule with `confidence: "low"` produces an `uncertainties` record, in addition to whatever items 2–4 produce.
2. **Missing required capture.** A required role (§4) is *missing* when its group did not take part in the match or captured the empty string (§6.5). A match with a missing required role produces an `uncertainties` record and **no** record of its type (no symbol, relation, db access, config ref or entry point). This applies to every rule type (§9 Q3, adopted for 1.0 by D16 f).
   - For `module_declaration` and `symbol_definition` this means an **unnamed definition**: it produces an `uncertainties` record, no `symbols` record, is never an enclosing symbol, and does not count as a module declaration for item 4 (D19 c). If its rule has `blockEnd`, it still pairs with its own `blockEnd` match (§6.6, D21).
   - An optional role that is missing is simply absent from the record.
3. **`symbol_definition` kind.** The Navigator kind is `function` when the `kind` capture is present and, lowercased, starts with `func`; otherwise (no `kind` role mapped, `kind` missing, or any other text) it is `procedure`. This is the 1.0 rule (§9 Q2).
4. **Source of `relations`, `dbAccesses` and `configRefs`** (D19 b). Every such record has a source, chosen in this order:
   1. the match's enclosing symbol: the innermost scope open at its start position (§6.6);
   2. if no scope is open there: the `name` of the last `module_declaration` match in the same file whose start position is before the match's start position, counting only named module declarations (item 2); whether that declaration's rule has `blockEnd`, or whether its scope has already been closed, does not matter;
   3. if the file has no such module declaration before the match: the file itself, identified by its repository-relative path with `/` separators (the same string §6.1 matches `fileMatchers` against).

   Such matches produce normal records. A match of these types never produces an `uncertainties` record for lack of a source.

## 5. Validation rules

Each rule has a stable code. `lsc validate-ruleset` prints it, and the invalid fixtures are named after it.

### 5.1 Expressed in JSON Schema

| Code | Rule | Fixtures |
| --- | --- | --- |
| `contract-version` | `contractVersion` must be supported (§2). The schema expresses it as a pattern (`^1\.0\.(0\|[1-9]\d*)$`). The validator checks it first and stops, because the rest of a file in another format is meaningless. | `contract-version--major-2`, `contract-version--newer-minor` |
| `schema` | Structure: required fields, types, enums, formats, closed objects (no unknown fields), and the engine discriminator (`engine: "exact"` requires `exact` and forbids `regex`, and the reverse). Details in §7. | every `schema--*` file, including `schema--rule-type-branch-marker` and `schema--rule-type-exit` (D1) |

### 5.2 Not expressible in JSON Schema — consumers must run `lsc validate-ruleset` or reimplement these

Checked per rule unless stated. These run only on a structurally valid file.

| Code | Rule | Fixtures |
| --- | --- | --- |
| `duplicate-rule-id` | Rule `id` values are unique within the file. The second and later occurrences are reported. | `duplicate-rule-id--two-rules-same-id` |
| `captures-required-roles` | `captures` maps every required role of the rule's type (§4). | `captures-required-roles--call-without-callee` |
| `capture-role-not-allowed` | `captures` maps only roles that are required or optional for the rule's type (§4). Navigator would not know what to do with any other role. | `capture-role-not-allowed--name-on-db-read` |
| `capture-group-missing` | Every group name in `captures` exists: for `regex`, as a named group `(?<name>…)` in `regex.pattern`; for `exact`, as a placeholder token `(?<name>)` in `exact.tokens`. Unreferenced groups are allowed. | `capture-group-missing--regex-pattern`, `capture-group-missing--exact-placeholder` |
| `block-end-type` | `blockEnd` appears only on `module_declaration` and `symbol_definition` (D4). | `block-end-type--on-call` |
| `re2-compile` | `regex.pattern` and `blockEnd.pattern` compile under RE2 with their `flags` (D3). Lookaround, backreferences and possessive quantifiers are not RE2. Duplicate group names fail here too. If the rule pattern does not compile, `capture-group-missing` and `named-group-syntax` are not checked for it. | `re2-compile--lookahead`, `re2-compile--block-end-backreference` |
| `named-group-syntax` | Named groups use `(?<name>…)`. RE2 also accepts `(?P<name>…)`, but other regex engines do not, so the contract forbids it (D2). | `named-group-syntax--python-style` |
| `exact-tokens` | `exact.tokens` contains at least one literal token (a rule of placeholders only would match every word), and no placeholder name appears twice. | `exact-tokens--only-placeholders`, `exact-tokens--duplicate-placeholder` |

RE2 reference: the validator uses the `re2` npm package (Google RE2). A consumer reimplementing `re2-compile` must use an RE2 binding for its platform, not its native regex engine.

## 6. Matching semantics

This section is normative. A consumer must apply rules exactly like this, or its results will differ from what `lsc test` measured. The reference implementation is `src/engines/` (WP-04).

### 6.1 Which files and which rules

- A file is scanned when its repository-relative path, with `/` separators, matches at least one `fileMatchers` glob. Globs are case-sensitive and use only `**` (any number of path segments, including none), `*` (any characters except `/`) and `?` (one character except `/`).
- Only rules with `status: "validated"` are applied. Rules with `status: "rejected"` may appear in draft Rule Sets and must be ignored.
- `confidence` does not affect matching; it only adds `uncertainties` records (§4).

### 6.2 Lines

- Line numbers are 1-based. Lines are separated by `\n`; a `\r` at the end of a line is not part of the line and is removed before matching. Before whole-text matching, `\r\n` is replaced by `\n`.
- Columns are not part of the contract.

### 6.3 Masking comments and string literals

Masking replaces comment and string-literal text with spaces so that keywords inside them never match. Newlines are kept, so line numbers never change.

The file is scanned once from left to right, outside of any comment or string:
- At each position, check whether `blockComment.start`, `lineComment` or any `stringDelimiters[i].start` begins there. If several begin at the same position, the longest delimiter wins; on equal length, the order is block comment, line comment, then string delimiters in array order.
- **Line comment**: from the marker to the end of the line (the newline is not part of it).
- **Block comment**: from `start` through the next `end`, across lines; not nested. Unterminated: to end of file.
- **String literal**: from `start` through the next matching `end` **on the same line**. There are no escape sequences in 1.0 (§9 Q4). Unterminated on its line: to end of line.
- Inside a comment or string, no other delimiter is recognised (`--` inside a string is not a comment; `"` inside a comment does not start a string).

Two masked views of each file exist:
- **Full mask** (default): comments and string literals, including their markers and delimiters, become spaces.
- **Comment mask** (rules with `searchStrings: true`): only comments become spaces; string literals are kept verbatim. String detection still runs, so comment markers inside strings are still not comments.

A field that is absent disables that kind of masking. A Rule Set with none of the three fields matches on the raw text.

### 6.4 Engines

#### Regex engine (`engine: "regex"`)

- The pattern runs on RE2 with its `flags`: `i` case-insensitive, `m` `^`/`$` match at line breaks, `s` `.` matches `\n`. Flags are a subset of `ims`, in that order.
- `multiline: false` (per-line): the pattern runs on each masked line separately, without its line terminator.
- `multiline: true` (whole-text): the pattern runs once on the whole masked text. The match's line is the line containing its first character.
- All non-overlapping matches are found, left to right (like a global search). Zero-length matches are ignored.

#### Exact engine (`engine: "exact"`)

An exact rule is a sequence of tokens on one line. Each token is either:
- a **literal**: any string without whitespace, compared exactly, or case-insensitively when `caseSensitive: false`;
- a **placeholder**: a token that is exactly `(?<name>)`, which captures one run of ASCII word characters `[0-9A-Za-z_]+` under group `name`.

The meaning of an exact rule is defined by the RE2 regex it is equivalent to, applied per line like a regex rule with `multiline: false`:

- literal token → the token text with regex metacharacters escaped, preceded by `\b` if its first character is a word character and followed by `\b` if its last character is a word character;
- placeholder `(?<name>)` → `\b(?<name>[0-9A-Za-z_]+)\b`;
- consecutive tokens joined by `[ \t]*` (spaces or tabs, possibly none);
- flag `i` when `caseSensitive` is false, otherwise no flags.

So `["CALL", "(?<callee>)"]` with `caseSensitive: false` is `\bCALL\b[ \t]*\b(?<callee>[0-9A-Za-z_]+)\b` with flag `i`. It matches `call apply_discount(x)` (capture `apply_discount`) and does not match `RECALL_x` or `CALLx y`. Two word tokens always need at least one space or tab between them, because `\b` cannot hold between two word characters; punctuation tokens may touch their neighbours (`FLAG("a")` matches `["FLAG", "("]`).

The function `exactToRegex` in `src/contract/exact.ts` produces this regex and is the reference.

### 6.5 Captures

- A capture's value is the text of its group in the matched (masked) text.
- A mapped group that did not take part in the match gives no value for that role. A group that took part but captured the empty string also counts as missing. What a missing required role does to the match's records: §4.1 item 2.

### 6.6 Definitions, scopes and `blockEnd` (D4)

- A match of a `module_declaration` or `symbol_definition` rule **that has `blockEnd`** opens a scope of that rule. The scope is named by the match's `name` capture.
- A match of that rule's `blockEnd` pattern (same masked view as the rule, its own `flags` and `multiline`) closes the most recently opened, still open scope of **the same rule** (last in, first out per rule id). A `blockEnd` match with no open scope of that rule is ignored with a warning.
- An **unnamed definition** (its `name` capture is missing or empty, §6.5) of a rule with `blockEnd` still opens a scope for `blockEnd` pairing, so the pairing above counts it like any other definition of its rule: its own `blockEnd` closes it, and a `blockEnd` never skips it to close an older scope of the same rule. But that scope is **anonymous**: it is never an enclosing symbol and never a fallback source (§4.1 items 2 and 4). A match inside it gets the enclosing symbol it would have had without it, which is the innermost *named* scope open at its start position. The definition itself produces an `uncertainties` record and no `symbols` record (§4.1 item 2, D19 c, D21). Example with one rule `PROC … ENDPROC` whose name is optional: in `PROC outer` / `PROC` / `ENDPROC` / `CALL after()` / `ENDPROC`, the first `ENDPROC` closes the unnamed scope, and `after` is still enclosed by `outer`.
- Matches are processed in order of their start position in the file; at the same position, `blockEnd` matches are processed before rule matches.
- Every match gets as enclosing symbol the innermost named scope open at its start position (any rule; anonymous scopes are skipped). A definition does not enclose itself. A match with no open scope has no enclosing symbol; for `relations`, `dbAccesses` and `configRefs` the source then falls back to the last named module declaration before it, or the file (§4.1 item 4, D19 b).
- Scopes still open at end of file, named or anonymous, are closed there, with a warning, not an error.
- A definition rule without `blockEnd` opens no scope (§9 Q5). A `module_declaration` without `blockEnd` still acts as the fallback source of §4.1 item 4.

## 8. Changing the contract

The contract is frozen at Gate G1. After that, only `contract-architect` changes it, and every change needs all of:

1. `CONTRACT_VERSION` in `src/contract/version.ts` bumped according to §2.
2. `npm run contract:export` run and `contract/rule-set.schema.json` committed (a test fails otherwise).
3. This file updated, including new fixtures for any new validation rule (one failing fixture per rule; a test fails if a rule code has none).
4. A `docs/DECISIONS.md` entry.
5. Legacy Navigator told, with the new schema file, before a Rule Set with the new version is shipped.

## 9. Open questions

To be answered by the project owner (G1) or from real-language evidence (Wave 5). Changing any of these answers after G1 follows §8.

- **Q1 — Exact engine placeholders (D11).** The plan gives the exact engine only `tokens` and `caseSensitive`, yet every rule type requires a capture. Without a capture mechanism no exact rule could ever be valid. Contract 1.0 adds placeholder tokens `(?<name>)` matching `[0-9A-Za-z_]+`. If the real language's identifiers contain other characters (`.`, `-`, `$`, `#`), rules for them must use the regex engine.
- **Q2 — `symbol_definition` kind.** *1.0 rule (D16 f, as implemented in WP-04):* `kind` capture, lowercased, starting with `func` → `function`, else `procedure` (§4.1 item 3). **Still open for G4:** whether the real language needs a per-language mapping instead (a new optional field would be a minor bump).
- **Q3 — Missing or ambiguous captures.** *Resolved (D16 f, D19 c):* a missing or empty required capture produces an `uncertainties` record and no record of its type; an unnamed definition is never an enclosing symbol but still pairs with its own `blockEnd` (§4.1 item 2, §6.6, D21). **Still open for G4:** whether any other situation counts as "ambiguous captures" (plan §5.3); 1.0 defines none.
- **Q4 — Escapes in string literals.** 1.0 has none (a string ends at the first `end` delimiter). If the real language escapes quotes (`\"` or `""`), an optional `escape` field on the delimiter pair would be a minor bump.
- **Q5 — Definitions without `blockEnd`.** *Resolved (D19 b):* they still open no scope. Instead, a relation, db-access or config-ref match with no open scope takes as source the last named `module_declaration` before it in the file, or the file itself (§4.1 item 4). **Still open for G4:** nothing beyond checking this against the real language.
- **Q6 — Several comment markers.** `lineComment` and `blockComment` are single values, as in the plan. A language with two line-comment markers would need them as arrays: a major bump if replaced, a minor bump if added as new optional fields.
- **Q7 — Source file encoding.** The contract assumes text decoded as UTF-8. Legacy code may be Latin-1 or another code page; if so, a top-level `encoding` field is a minor bump.
- **Q8 — Newer minor versions.** §2 makes a consumer reject newer minors. The alternative is to let it skip unknown rule types and fields, which requires open (non-strict) objects and weakens typo detection.
- **Q9 — Matches outside any open scope (WP-04 question).** *Resolved (D19 b):* they produce normal records with the fallback source of §4.1 item 4, never a `missing-source-symbol` uncertainty. Details fixed by `contract-architect` in D20 where D19 was silent, to be confirmed by the project owner: only *named* module declarations count as fallback source; the file is identified by its repository-relative path. *Resolved in 1.0.2 (D21):* an unnamed definition of a rule with `blockEnd` opens an anonymous scope. The scope takes part in same-rule `blockEnd` pairing (its own `blockEnd` closes it), but it is never an enclosing symbol or fallback source (§6.6). The 1.0.1 text, under which its `blockEnd` closed the most recent open scope of the same rule, is withdrawn: with nested same-rule definitions it ended the outer scope early and misattributed the matches after it. **Still open:** how Navigator tells a file source from a symbol name in its records (Navigator's record shape, outside this contract).
