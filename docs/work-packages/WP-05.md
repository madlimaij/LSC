# WP-05 — Test runner

- **Owner:** `engine-builder`
- **Depends on:** WP-04
- **Owns:** `src/runner/`, `src/cli/commands/test.ts`

## Goal

Measure any Rule Set against labelled examples and a repository sample, fully offline. This is both the compiler's quality check and the proof that routine scanning needs no LLM.

## Deliverables

- `runRules(ruleSet, examples, sampleFiles?) → Results`
- Per rule: passed/failed examples following plan §6.2, missed expected matches, unexpected matches, wrong captures (expected vs actual), and unlabelled sample matches with file, line and a ±3-line snippet
- Cross-construct negatives: each rule is also run against negative examples of other constructs
- Confidence computed with the fixed formula in plan §6.3 (D8), implemented once and exported for WP-09 and WP-10
- Coverage summary: which rule types have a validated rule, which constructs have too few examples for `high`
- `Results` saved as JSON (`results.json`) with a Zod schema, because WP-07 and WP-09 consume it
- CLI: `lsc test <ruleset> <skills-dir> [--sample <dir>] [--out results.json]`; exit code non-zero when any rule fails

## Acceptance criteria

- The toylang fixture Rule Set passes all toylang examples; any discrepancy is reported to the orchestrator for `contract-architect` to fix in the fixture
- A deliberately broken copy of the fixture produces the expected misses, false positives and wrong-capture entries (tested)
- The run makes no network calls (test with network access blocked or the LLM module not imported)
