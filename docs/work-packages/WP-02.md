# WP-02 — Rule Set contract

- **Owner:** `contract-architect`
- **Depends on:** WP-01
- **Owns:** `src/contract/`, `contract/`

## Goal

Implement the contract in plan §5 exactly, so it can be frozen at Gate G1 and shared with Legacy Navigator.

## Deliverables

- Zod schemas and inferred TypeScript types for Rule Set and Rule (plan §5.1–5.2), with `engine` as a discriminated union
- Rule type enum and a `RULE_TYPE_SPEC` table: rule type → Navigator record kind, required capture roles, optional roles (plan §5.3)
- Cross-field validation:
  - `captures` include every required role of the type
  - every capture group name referenced exists in the pattern
  - `blockEnd` only on `module_declaration` and `symbol_definition`
  - patterns compile under RE2 (D3)
  - rule `id` values are unique
- `contract/rule-set.schema.json` generated from Zod by a script (`npm run contract:export`), committed, and checked in a test to be up to date
- `contract/CONTRACT.md`: human-readable contract including the mapping table and the version-bump rules
- `contract/fixtures/toylang.ruleset.json`: a hand-written valid Rule Set covering every rule type for toylang (as specified in WP-03)
- `contract/fixtures/invalid/*.json`: at least one file per validation rule above, each failing for exactly that reason
- CLI command `lsc validate-ruleset <file>` with readable errors (JSON path + message)

## Acceptance criteria

- The valid fixture passes; each invalid fixture fails with an error naming the violated rule
- JSON Schema validation (with a standard validator in the test) accepts the valid fixture and rejects the structurally invalid fixtures
- `contractVersion` is `1.0.0`

## Notes

- Do not add `branch_marker` or `exit` (D1).
- Cross-field checks that JSON Schema cannot express must be documented in `CONTRACT.md` so Navigator knows to run `lsc validate-ruleset` or reimplement them.
