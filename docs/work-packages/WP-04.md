# WP-04 — Rule engines

- **Owner:** `engine-builder`
- **Depends on:** WP-02, WP-03
- **Owns:** `src/engines/`

## Goal

Apply a single rule to a file's text deterministically and fast, returning matches with named captures and the enclosing definition.

## Deliverables

- Engine interface: `match(rule, preparedFile) → Match[]`, where `Match = { ruleId, type, line, column, captures, enclosingSymbol? }`
- `exact` engine: token sequence, respecting `caseSensitive`
- `regex` engine using RE2 only (D3); per-line by default, whole-text when `multiline: true`, with correct line numbers either way
- File preparation: comment and string masking using `lineComment`, `blockComment`, `stringDelimiters` from the Rule Set, replacing masked characters with spaces so columns and line numbers are preserved
- Block tracking (D4): definition rules with `blockEnd` open and close scopes; every non-definition match gets `enclosingSymbol` = innermost open definition; unclosed blocks at end of file are reported as warnings, not errors
- Match-to-Navigator mapping function: `Match[]` → `NormalizedFileAnalysis`-shaped output (`symbols`, `relations`, `dbAccesses`, `configRefs`, `entryPoints`, `uncertainties`) using `RULE_TYPE_SPEC`; low-confidence matches also produce an uncertainty
- Performance guard: a test scanning a generated 50 000-line toylang file with the fixture Rule Set completes under a set time budget (record the measured time)

## Acceptance criteria

- Unit tests for each engine, masking, block tracking (including nested blocks and unclosed blocks) and mapping
- A keyword inside a comment or string never matches when masking is configured
- The mapping output for one full toylang file matches a committed snapshot

## Notes

- Masking can hide legitimate matches where strings carry meaningful identifiers (for example a table name passed as a string). Honour the rule field `searchStrings: true` by matching that rule against the unmasked strings.
