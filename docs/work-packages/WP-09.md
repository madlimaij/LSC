# WP-09 — Rule synthesis and refinement loop

- **Owner:** `llm-integrator`
- **Depends on:** WP-05, WP-06, WP-08
- **Owns:** `src/synth/`, `src/cli/commands/compile.ts`

## Goal

Produce validated rules from Skill files and examples without hand-written regexes (plan §8).

## Deliverables

- Proposal prompt per construct: the construct's bounded Skill prose, its examples (bounded), the contract excerpt for the target rule type (required captures, RE2 constraints), and instructions:
  - prefer `exact` over `regex`
  - use named captures
  - propose nothing if the documentation does not justify a rule, and say why
- Response schema: `{ rules: RuleDraft[], notJustified?: string }`
- Pipeline per construct:
  1. propose
  2. validate with the contract schema and RE2
  3. run with the WP-05 runner against its examples plus cross-construct negatives
  4. on failure, refine with the failing examples, expected vs actual matches, and the previous pattern
  5. stop at the attempt cap (default 3)
- Rules get `sourceEvidence`, `tests` and computed confidence (D8); rules that never pass are kept in `results.json` as `rejected` with their last pattern and failure reasons
- `lsc compile <skills-dir> [--sample <dir>] [--provider <name>]` writes a draft Rule Set, `results.json` and the report (WP-07)
- Recordings for a full toylang compile, so the whole pipeline runs in tests via `FakeProvider`

## Acceptance criteria

- A full toylang compile via `FakeProvider` yields a Rule Set that passes `lsc validate-ruleset` and covers every rule type
- A recorded "bad first proposal" case shows refinement fixing it within the cap
- A recorded case that never converges ends as `rejected`, visibly, without crashing the compile
- Repository-sample file contents never appear in the snippet log (tested)
- One manual run against a real provider on toylang is documented in the completion note: rule count, pass rate, token usage
